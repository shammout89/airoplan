# AeroPlan 0.15.0 — سياسة اعتماد خطة الصيانة

يضيف الإصدار قسم «الإعدادات ← سياسة الاعتماد»، ومسارًا محفوظًا لكل طلب، وسجلًا للقرارات ومقارنة بالتعريف المعتمد السابق. تبقى الحسابات وكلمات المرور والطائرات والتقدم السابق محفوظة.

| الإعداد / الإجراء | السلوك |
| --- | --- |
| الإعداد الافتراضي | مُعدّ، ثم مراجع فني مستقل، ثم معتمد مستقل |
| مسار الشخصين | مُعدّ، ثم معتمد مستقل يجري المراجعة الفنية ويعتمدها مع تأكيدات ونتيجة مكتوبة |
| التعديل الإداري | الملاحظة الإدارية المخصصة فقط بعد اعتماد سابق |
| الإنشاء والتعديل الفني | اسم المهمة، الطائرة، المرجع، حدود FH/FC/التاريخ، البرنامج، الحقول المخصصة وأي تغيير آخر |
| اختيار المسار | يحدده الخادم من التغيير والسياسة المحفوظة؛ لا يختاره المُعدّ |
| تعديل السياسة | للمالك فقط، بإصدار جديد ومرجع إجراء وسبب؛ تبقى الطلبات المحفوظة والجارية بسياستها |
| تعطيل الحساب / سحب الصلاحية | يمنع الإجراءات التالية فورًا، ويُفحص أيضًا عند تثبيت القرار في قاعدة البيانات |
| الإنجاز والإغلاق | يحتفظ بمراجعته واعتماده المستقلين؛ لا تقصّره سياسة التخطيط |

يستطيع المالك اختيار مسار الشخصين للفني أيضًا إذا سمح إجراء الشركة بذلك وأكد المسؤولية الفنية للمعتمد. لا يسمح النظام بجعل المسار الفني أقل تدقيقًا من الإداري. تغيير اسم المهمة فني لأنه قد يصف العمل المطلوب. يبقى التغيير الفني فنيًا داخل دورة الطلب ولو تلاه تعديل ملاحظة أو إعادة القيمة القديمة.

## تحديث التثبيت القائم

حزمة `AeroPlan-Approval-Policy-Update-0.15.0.zip` تراكمية للمصادر 0.14.6 و0.14.7 و0.14.8. نزّلها إلى Downloads. استخدم هذه الحزمة فوق المجلد الحالي؛ النسخة الكاملة مخصصة أيضًا للتثبيت الجديد. احتفظ بنسخة كاملة صالحة للاستعادة قبل التحديث وفق إعداد النسخ الموجود لديك.

شغّل Docker Desktop، ثم نفّذ في **نافذة PowerShell واحدة**. هذه أوامر مباشرة، فلا تحتاج إلى تشغيل ملف ps1 أو تغيير سياسة التنفيذ.

**1. تحقق من المجلد والحزمة والإصدار قبل الكتابة:**

```powershell
set-location -literalpath "$env:userprofile\downloads\aeroplan-docker"
$aeroupdate = "$env:userprofile\downloads\AeroPlan-Approval-Policy-Update-0.15.0.zip"
if (-not (test-path -literalpath $aeroupdate -pathtype leaf)) { throw "Download AeroPlan-Approval-Policy-Update-0.15.0.zip into Downloads first." }
$aerosource = get-content -literalpath '.\release.json' -raw | convertfrom-json
if ($aerosource.version -notin @('0.14.6','0.14.7','0.14.8','0.15.0')) { throw "This update supports source 0.14.6, 0.14.7 or 0.14.8. Check the source folder." }
write-host "Source:" $aerosource.version
```

**2. استخرج التحديث داخل مجلد البرنامج نفسه:**

```powershell
expand-archive -literalpath $aeroupdate -destinationpath "$env:userprofile\downloads\aeroplan-docker" -force -verbose
get-content -literalpath '.\release.json'
```

المتوقع `version: 0.15.0`. الحزمة لا تتضمن compose.yaml أو البيئة أو البيانات أو الأسرار أو إعدادات Compose المُنشأة للخدمات والنسخ.

**3. احتفظ بملفات التشغيل الحالية وأعد البناء:**

```powershell
$aerofiles = @('-f', 'compose.yaml')
if (test-path -literalpath '.\compose.production.yaml') { $aerofiles = @('-f', 'compose.production.yaml') }
foreach ($aeroextra in @('compose.backup.yaml', 'compose.services.yaml')) { if (test-path -literalpath $aeroextra) { $aerofiles += @('-f', $aeroextra) } }
write-host "Starting AeroPlan 0.15.0 with the existing aeroplan project..."
docker compose -p aeroplan @aerofiles up -d --build --force-recreate --wait
if ($LASTEXITCODE -ne 0) { throw "Docker startup failed. Run: docker compose -p aeroplan logs --tail 80 app" }
```

أوامر تعيين المتغيرات لا تطبع مخرجات؛ هذا طبيعي. انتظر انتهاء البناء وعودة مؤشر PS. يبقى مشروع `aeroplan` ووحدة بياناته، ولا يحتاج المدير إلى إعادة تهيئة. قد يحتفظ وسم الصورة باسمه القديم لأن ملف Compose محفوظ؛ إصدار البرنامج الفعلي يثبته healthz.

**4. تحقق من الحاوية العاملة:**

```powershell
invoke-restmethod 'http://localhost:8080/healthz' | format-list status, version, buildFingerprint
docker compose -p aeroplan @aerofiles ps
```

المتوقع `status: ok` و`version: 0.15.0` والبصمة:

`069ccbe05899e5488bfe526deba296c09438cb6df9af46da62ccd00097b25aff`

إذا بقي إصدار قديم، لا تكرر استخراج الملفات عشوائيًا: تحقق من المجلد الحالي وملفات Compose التي شغّلتها ومشروع الحاوية، ثم اقرأ سجل البناء. رقم release.json للمصدر وحده لا يثبت تحديث الحاوية.

## ما الذي ستراه؟

اضغط Ctrl+F5، ثم ادخل بحساب المالك وافتح:

[سياسة الاعتماد](http://localhost:8080/?settings=policy)

تظهر سياستا الإداري والفني، والأدوار المؤهلة، وإلزام المستند، ومرجع إجراء الشركة، وسبب التغيير وسجل الإصدارات. تظهر الشاشة للمدير والمراجع والمعتمد حسب صلاحياتهم، ويكون تعديل السياسة للمالك فقط. إدارة الحسابات والدور والحالة تبقى في «المستخدمون والصلاحيات».

في «خطة الصيانة»، يظهر رابط **مسار الاعتماد وسجله ↖**. يعرض السياسة المثبتة، ونوع التغيير، والنسخة الحالية للطائرة وعداداتها، والمستندات المنشورة للتنزيل، والتغييرات عن الاعتماد السابق، والقرارات مع الدور وقت القرار. في مسار الشخصين يظهر **مراجعة واعتماد**؛ يلزم تأكيد مراجعة الهوية والانطباق والحدود والمصادر والأدلة والتغييرات، وكتابة نتيجة مراجعة فنية. يسجل النظام الشخص نفسه مراجعًا ومعتمدًا في هذا المسار بوضوح، دون ادعاء وجود توقيعين مستقلين.

تظل الطلبات القديمة على المسار المستقل لثلاثة أشخاص. لا تتغير الطلبات المحفوظة بإعداد سياسة أحدث. عند الحاجة للتصحيح، أعد الطلب قيد المراجعة للمسودة بسبب واضح. يبقى تحت سياسته الأصلية؛ يبدأ تعديل مهمة معتمدة دورة جديدة بالسياسة الحالية. حفظ البيانات دون تغيير فعلي لا يلغي الاعتماد.

## اختبارات القبول على جهازك

نفّذ الاختبارات على بيانات TEST وفي بيئة تجريبية. اترك سياسة التشغيل متوافقة مع إجراء الشركة المعتمد.

1. **ثلاثة أشخاص:** أنشئ مهمة اختبار جديدة تحت السياسة الافتراضية، أرسلها من المخطط، راجعها من المراجع، ثم اعتمدها من المعتمد. يجب أن تبقى بعد المراجعة «بانتظار الاعتماد المستقل» حتى توقيع المعتمد.
2. **شخصان:** في بيئة الاختبار، اجعل الإداري شخصين والفني ثلاثة، وسجل مرجع الإجراء وسبب التغيير والتأكيد. عدّل الملاحظة الإدارية فقط في مهمة اختبار معتمدة، وأرسلها. يجب أن يرى المعتمد «مراجعة واعتماد»، وأن يرفض الخادم القرار دون التأكيدات والنتيجة المكتوبة. لا يملك المراجع زر اعتماد نهائي.
3. **تعديل فني:** غيّر حد FH أو FC أو المرجع أو اسم المهمة. يجب أن يختار الخادم المسار الفني، وأن يبقى كذلك بعد تعديل ملاحظة لاحق. لا يعدّل المستخدم نوع التغيير بيده.
4. **الاستقلال:** جرّب مراجعة أو اعتماد مهمة ساهم الحساب نفسه في إعدادها أو إرسالها. يجب أن يرفضها النظام حتى بعد تغيير دور الحساب. في مسار الثلاثة لا يعتمد المراجع مراجعته، ولو أصبح دوره معتمدًا.
5. **السياسة أثناء العمل:** غيّر السياسة بعد حفظ مسودة أو إرسال طلب. يجب أن يبقى الطلب على الإصدار والمسار المثبتين، وأن تبدأ الدورة الجديدة التالية بسياسة الإعداد الحالية.
6. **النسخة القديمة والأدلة:** افتح نافذة القرار، ثم عدّل المهمة أو بطاقة الطائرة من جلسة أخرى. يجب رفض النسخة القديمة، مع إبقاء النص المكتوب وإتاحة تحديث النسخة. تغير المستندات المنشورة بعد الإرسال يتطلب إعادة الطلب للمسودة ومراجعته مجددًا.
7. **الحسابات:** عطّل حسابًا أو اسحب صلاحية الاعتماد، ثم حاول استخدام جلسته السابقة. يجب أن يرفض الإجراء. تبقى كلمات المرور والحسابات والمصادقة الإضافية الحالية محفوظة.
8. **التقدم السابق:** تحقق من الطائرات والقوائم والتواريخ والمهام والمستندات والمستخدمين، ثم سجّل إنجازًا تجريبيًا. يجب أن يظل إرسال الإنجاز ومراجعته واعتماده وإغلاق المهمة مسارًا مستقلًا.
9. **العرض:** جرّب عرضًا ضيقًا ونافذة قصيرة، ومرر سجل الاعتماد حتى آخره. يجب بقاء العنوان والأزرار ظاهرين، وعدم تمرير الصفحة الخلفية، وعودة تمريرها بعد الإغلاق. جرّب التنقل بلوحة المفاتيح.
10. **النسخ والاستعادة:** نفّذ استعادة تجريبية على نسخة معزولة، وتحقق من سياسة الطلب وسجله وترتيب القرارات. النسخ الدلالية الجديدة v12؛ يقبل الإصدار أيضًا فحص واستعادة v11 السابقة. إعدادات السياسة الحالية محمية أثناء استعادة بيانات الأعمال، والطلبات تستأنف وفق سياستها المحفوظة.

لا ترجع إلى برنامج أقدم فوق بيانات تحتوي مسارات الاعتماد الجديدة. عند الحاجة للرجوع، استخدم مصدر الإصدار السابق ونسخته الكاملة المطابقة في وجهة منفصلة وفق دليل الاستعادة.

## نتيجة التحقق قبل التسليم

نجح TypeScript وبناء الإنتاج وجميع مجموعات الاختبار الـ41، بما فيها 204 تحققات لسياسة الاعتماد، و70 للواجهة مع 6 طلبات كتابة فعلية منها، و219 عبر خادم إنتاج محلي فعلي. شملت الاختبارات تعارض القرارات وسحب الصلاحيات قبل التثبيت وتغيّر الأدلة والبيانات القديمة والاستعادة الدلالية الفعلية والنسخ الكامل المشفر والدخول بعد الاستعادة. الأعداد تحققات متداخلة وليست حالات مستقلة قابلة للجمع.

نجحت أيضًا تجربة الحزمة التراكمية فوق المصادر 0.14.6 و0.14.7 و0.14.8، مع بقاء 12 عينة من ملفات التشغيل والبيانات والأسرار دون تغيير لكل إصدار، وإعادة بناء واختبار المصدر المستخرج بعد ترقيع 0.14.6.

اختبارات الواجهة DOM وCSS إنتاج؛ لم يبدأ Chromium في بيئة التحضير بسبب منع socket قبل فتح أي صفحة. لم تُشغل حاوية Windows/Docker ولم يُتحقق بصريًا من جهازك أو يُسجل قبول شركة حقيقي. يلزم تنفيذ قائمة القبول أعلاه بعد التثبيت؛ لا يسجل التقرير هذه البنود كناجحة مسبقًا.
